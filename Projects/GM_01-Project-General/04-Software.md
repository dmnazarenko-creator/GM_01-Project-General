# Описание программного обеспечения

> Статус: рабочий проект; неутверждённые технические решения отмечены отдельно.
> Регламент: [rules.txt](../../rules.txt); корпоративный стиль: [WAS.txt](../../WAS.txt), [WAS.pdf](../../WAS.pdf).
> Дата: 2026-11-12.

## 1. Конфигурация

Прошивка поддерживает системную команду Modbus, сохраняющую адрес Slave и скорость интерфейса RS-485 в энергонезависимой памяти. После записи должны выполняться проверка параметров и безопасное применение новой конфигурации; процедура восстановления доступа после ошибки пока не определена.

## 2. Индикация

Программа управляет LED1 по режиму работы. LED2 активируется только при обработке кадров, предназначенных этому устройству; кадры с чужим индивидуальным адресом игнорируются для индикации. Для групповых и широковещательных запросов поведение необходимо уточнить.

## 3. Кнопка

Удержание кнопки более 15 секунд инициирует восстановление параметров связи (скорость 9600 бит/с); адрес 1 предложен как вариант и не утверждён.

## 4. Обновление прошивки

Приём прошивки блоками по **128 байт (64 слова Modbus)**; регистрация последовательности и целостности блоков; контроль полного образа; проверка подлинности криптографическим механизмом; активация новой прошивки только после успешных проверок. Загрузчик/резервный механизм должны позволять восстановиться после прерывания обновления.

Алгоритм загрузчика, структура метаданных блока, протокол повторной передачи и безопасный откат пока не утверждены.

## 5. Алгоритм рассылки GM_05

Подготовительная команда устанавливает в GM_05 временный набор адресатов: явный список (например, **5, 7, 12, 15**) либо диапазон (**10–25**). Следующий предназначенный GM_05 шаблонный запрос получает идентификатор операции и направляется последовательно каждому выбранному Slave нижней линии. Перед отправкой каждой копии заменяется адрес Slave и пересчитывается CRC16 Modbus. GM_05 не должен менять код функции, регистры или полезные данные без отдельно определённого преобразования. Нижняя шина обслуживается по очереди; ответы Slave должны вычитываться и сопоставляться с адресами, прежде чем отправлять следующую команду.

Требуется спроектировать автомат состояний: IDLE → ARMED → DISPATCHING → COMPLETE/ERROR; запрет использования устаревшего шаблона, тайм-аут режима ARMED, контроль числа адресатов, поведение при рестарте, недопущение повторного исполнения после потери квитанции, сохранение результата поадресно. **Способ доставки шаблона и формат сводного результата пока не утверждены.**

## 6. Сброс коммуникационных настроек

Удержание кнопки **более 15 с** запускает процедуру восстановления связи: скорость 9600 бит/с и предлагаемый индивидуальный адрес 1. Адрес 0 не подходит для обычного конфигурирования с ответом, так как зарезервирован для broadcast. Адрес **1 рекомендуется, но окончательно не утверждён**; несколько сброшенных устройств следует конфигурировать индивидуально либо предусмотреть специальную процедуру идентификации по уникальному серийному номеру. Сброс не затрагивает защищённый загрузчик и ключи проверки подписи.

## 7. Протокол загрузчика и буферизация Flash

Ввести логическое окно регистров Modbus (не прямые адреса микроконтроллера): команда **BEGIN / WRITE_BLOCK / VERIFY / ACTIVATE / ABORT**, состояние **IDLE / RECEIVING / PROGRAMMING / VERIFYING / ERROR**, идентификатор и совместимость образа, общую длину, смещение и длину передаваемого блока, данные, ожидаемую CRC, подтверждённое смещение и код ошибки.

Получение прошивки должно допускать **блок 128 байт (64 регистра)**. Альтернативная детализация записи в RAM по 16 байт — допустимый вариант реализации, не утверждённый как основной транспорт. Данные буферизуются до целой физической страницы/единицы записи Flash, пишутся в резервную область и **читаются обратно для проверки**. Не стирать одну и ту же страницу при каждом фрагменте. Не использовать в сообщениях абсолютные адреса Flash; адрес назначения определяется после проверки bounds: `reserve_base + image_offset`, чтобы исключить загрузчик, настройки и метаданные.

После завершения загрузки проверять CRC **по считанному из Flash полному образу** и отдельно криптографическую подпись его хеша вместе с типом устройства, версией и ограничениями совместимости. CRC не подтверждает авторство. Выбор Ed25519 или ECDSA P-256, библиотеки, размера ключей и размещения хранилища доверия — открытый проектный вопрос; не считать приведённые ориентировочные размеры библиотек гарантированными. Закрытый ключ должен оставаться вне устройства; в MCU доступен только проверочный открытый ключ или его доверенный хеш.

## 8. Восстановление после сбоя питания

Предполагаемая последовательность: загрузка в резерв → проверка из Flash → надёжная запись метаданных «образ готов» → перезагрузка → загрузчик устанавливает резервный образ → проверяет рабочую область → запускает приложение. При пропадании питания установка возобновляется из целого резервного образа. При недействительном рабочем приложении загрузчик остаётся доступен через Modbus, с фиксированными/восстанавливаемыми параметрами связи. Прежде чем утверждать архитектуру, требуется проверить, достаточно ли у конкретного MCU встроенной Flash для резервного образа; иначе потребуется внешняя память или иной безопасный метод обновления.

Две копии метаданных с поколением и CRC располагаются в независимо стираемых областях: нельзя уничтожать единственную действительную запись при обновлении. **Восстанавливаемая установка не тождественна откату на старую версию**; настоящий rollback требует сохранения предыдущего образа или A/B.

## 9. Хранение настроек во Flash (проектное решение)

Вместо предполагаемой отдельной EEPROM использовать журналируемые записи в двух независимо стираемых областях Flash: заголовок/магическое число, версия формата, номер поколения, длина данных, настройки, CRC. Порядок байтов и сериализация должны задаваться явно; нельзя вычислять контрольную сумму по неопределённым padding-полям C-структуры.

При изменении: прочитать обе копии → выбрать самую новую валидную → подготовить новые значения в RAM → стереть **неактивную** область → записать обновлённую копию → прочитать и проверить → сохранить старую копию до успешной фиксации. Записывать только при реальном изменении, объединять изменения, учитывать износ и не смешивать области настроек с резервом прошивки. Особенности программирования CH32V203, watchdog и задержек Flash-операций необходимо подтвердить по SDK. Операции записи организовать в основном автомате состояний, а не внутри прерывания USART.
